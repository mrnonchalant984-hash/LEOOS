# LeonardX master directive — section-by-section gap audit

**Baseline:** the user-supplied `LEOOS-main (1).zip` uploaded 2026-11-15, compared with this handoff source tree.

**Scope:** the exact 20-section directive titled **“MASTER DIRECTIVE: LEONARDX COMPLETE PRODUCTION IMPLEMENTATION AND LAUNCH”**. This audit is deliberately stricter than checking whether a page, button, route, or script exists. A capability is not considered verified merely because its interface or integration boundary exists.

## Summary

The repository already contains a substantial LeonardX product: project and website builders, chat, image/document handling, agent/workforce modules, workflows, MCP, a LeoCode extension and sandbox bridge, Supabase persistence, Vercel integrations, voice, and operational scripts. The latest handoff adds chat image attachment plumbing, workflow/build diagnostics, verification utilities, and a release-readiness surface.

This is **not yet a production-verified release**. The current work closes several real chat UX gaps and provides a traceable audit of the remaining scope. Dependency installation, tests, typecheck, build, remote Supabase/RLS, live Gemini, browser QA, and production deployment remain intentionally unrun for the laptop owner.

## Additional product-level gaps identified

1. **Whole-product visual consistency:** the latest visual changes are concentrated in the Leo chat workspace and shared shell. The prompt requires inspection of every important existing route and responsive state.
2. **Chat-to-Work continuity:** the new mode switch is a truthful route into the existing engineering workspace. It does not yet convert a chat thread into a durable Work project with linked attachments, task plan, and acceptance criteria.
3. **Conversation indexing:** individual conversations persist, but the recent-chat index is still locally maintained. Cross-device history indexing is not demonstrated.
4. **Image upload telemetry:** upload feedback is indeterminate, not percentage-based. Staging should establish whether a progress callback can be added without replacing the current fetch/storage flow.
5. **LeoCode runtime:** a package manifest and VSIX do not prove the extension runs. Extension Development Host, actual tool execution, file diff, cancellation, and recovery remain required.
6. **Sandbox proof:** a configured gVisor runtime or host script does not prove containment. The dedicated runner needs a live isolation acceptance and security review.
7. **Worker durability:** checkpoint and yield code does not prove scheduler invocation, queue leases, idempotency, or recovery after process termination. Exercise real worker failure and resume paths.
8. **Vercel HTTP 500:** improved diagnostics are not a root-cause repair until a reproducible staging failure is correlated to logs and the corrected deployment succeeds.
9. **Unified context:** shared provider infrastructure is not enough. Verify equivalent identity, permissions, memory, project context, and tools across every Leo interface.
10. **Remote security and deployment:** no remote RLS, live Gemini, live Vercel deployment, payment, OAuth, or production acceptance test was run.

## Laptop verification order

1. Install root and LeoCode extension dependencies using the lockfiles.
2. Run focused chat UX and attachment tests, then the full unit/integration suite.
3. Run lint, TypeScript typecheck, and production build; repair failures without suppressing them.
4. Compile and test LeoCode; launch VS Code Extension Development Host and perform the runtime acceptance checklist.
5. Run sandbox host preflight and the isolated-container smoke test on the dedicated runner.
6. Deploy to a staging/preview environment with staging Supabase and provider credentials only.
7. Run remote RLS, live Gemini image/voice, worker recovery, build/deploy HTTP 500 reproduction, and responsive browser tests.
8. Review all evidence and only then decide whether the release gates pass.
9. Push to GitHub or deploy to production only after explicit authorization.

# Android builds through MCP

`build_android_calculator` creates and persists a real Java Android calculator project, then returns a queued job ID. A separate authenticated worker claims the job from Supabase, invokes `gradle :app:assembleDebug`, validates APK signature/size/SHA-256, and uploads it to the existing private `leo-files` bucket. `get_android_build_status` returns persisted progress and an authenticated download endpoint only after completion. The artifact endpoint re-downloads from private storage and re-verifies byte count and checksum before returning bytes.

## Server requirements

- Node.js runtime with Java 17 or newer available as `JAVA_HOME`/`PATH`.
- Gradle 8.9 or compatible Gradle 8.x available as `GRADLE_HOME`/`PATH`.
- Android SDK platform 35 installed and discoverable as `ANDROID_HOME` or `ANDROID_SDK_ROOT`.
- The base artifact migration `supabase/migrations/20261019100000_android_build_artifacts.sql` is already recorded in the linked database. Apply the forward worker migration `supabase/migrations/20261019120000_android_build_worker_queue.sql`; it fails if `leo-files` is absent, sets the bucket private, and raises its per-file limit to at least 150 MiB. Supabase project-level quota and remaining capacity must still be checked in the project dashboard.
- The worker migration creates a single-concurrency, lease-based queue. A worker restart is recovered when its 15-minute lease expires. Caught failures retry with backoff up to three attempts; expired leases are reclaimed up to three times.
- For the hosted GitHub Actions worker, add repository Actions secrets `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` pointing to the same production Supabase project used by LeonardX. After the workflow is on the default branch, the queue/finalization migrations are applied, and the secrets are verified in GitHub Settings (never read or print their values), set the non-secret Vercel environment flag `ANDROID_HOSTED_WORKER_ENABLED=true` so capability discovery can report the hosted-worker configuration. This flag is an operator declaration, not a live health check.
- The optional `/api/workers/android-build` endpoint is only for a compatible self-hosted runtime with the full Android toolchain; only for that mode configure `ANDROID_BUILD_WORKER_ENABLED=true` and a random `ANDROID_BUILD_WORKER_SECRET` of at least 32 characters on the server and trusted scheduler. Keep the secret only in the scheduler and server environment.
- The implementation ZIP includes `.github/workflows/android-build-worker.yml`, a hosted worker scheduled every five minutes and manually triggerable from GitHub Actions. This is a GitHub Actions schedule, not a Vercel Cron. It does not add or alter entries in `vercel.json`, so Vercel Hobby's daily-only Cron limit is respected. It runs on a GitHub-hosted Ubuntu runner with JDK 17, Android API 35/build-tools 35.0.0, and checksum-verified Gradle 8.9. The workflow must exist on the default branch, GitHub Actions and scheduled workflows must be enabled, and repository Actions secrets `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` must point to the same production Supabase project used by LeonardX. The service-role secret is available only to the worker step; it is explicitly removed from the environment passed to Gradle. Never commit or paste these secret values.
- Each hosted worker run claims at most one job through the atomic database RPC, records its first `started_at`, heartbeats the lease, compiles the persisted project, checks the APK archive, verifies its Android signature with `apksigner`, checks package metadata with `aapt`, computes SHA-256 from the final bytes, and uploads to the existing private `leo-files` bucket. Before compiling, it searches for an already-uploaded artifact belonging to that exact owner/job, validates it, and finalizes it if valid, avoiding a duplicate Gradle build after a crash between upload and database finalization. Artifact names include the checksum so stale workers cannot overwrite another build's bytes. A forward migration adds atomic lease-owned finalization; only the worker holding a live lease can complete or retry the row. A crashed job becomes eligible after its 15-minute lease expires; caught failures use bounded exponential backoff and a maximum of three attempts.
- The Vercel `/api/workers/android-build` endpoint remains for compatible self-hosted runtimes, but it now fails closed before claiming a job if Java, Gradle, or Android SDK is absent. Standard Vercel serverless does not magically acquire these tools just because the endpoint exists. `Dockerfile.android` remains a reproducible self-hosted alternative with Node 22 + JDK 17 + Gradle 8.9 + Android API 35. It pins official download checksums; building it invokes `sdkmanager --licenses`, so the operator must review and accept Google's SDK terms. Do not pass Supabase keys or worker secrets as Docker build arguments; supply them only as runtime secrets.
- GitHub Actions cron is not guaranteed to run at an exact minute and only runs from the repository's default branch. If Actions or the required secrets are not configured, source changes alone do not start the worker. Check the workflow run history and the authoritative job row before claiming recovery. The job can be downloaded only through LeonardX's authenticated, owner-scoped endpoint; the private Storage path is never a public download URL.
- The enqueue API returns `202` promptly; clients poll `get_android_build_status` with the returned job ID. The existing authenticated MCP user token is required for owner-scoped status and downloads.

The enqueue endpoint is authenticated with a LeonardX session or MCP OAuth token. MCP callers need `mcp:write` to start a build and `mcp:read` to inspect/download it. Build attempts are owner-scoped and deduplicated by UUID idempotency key; each account is additionally limited to one start per hour. The calculator project is only created once a build request passes authentication and mobile-plan entitlement. The artifact bucket must remain private; the download route authorizes ownership and checks the stored checksum for each request.

## Connecting an MCP client

Deploy LeonardX at a stable public HTTPS origin, configure `MCP_PUBLIC_URL` (or the supported site-origin setting) to that origin, apply the MCP OAuth migrations, and verify the OAuth discovery/protected-resource endpoints are reachable. Add `https://<your-origin>/mcp` as a remote MCP server in the client and complete LeonardX sign-in/consent. Grant `mcp:write` only when project creation/build tools are wanted; read-only connections can use `mcp:read`. The client must support Streamable HTTP MCP and OAuth. After deployment, an operator with a short-lived read token can run `npm run test:mcp:external` with `LEONARDX_MCP_URL=https://<your-origin>/mcp` and `LEONARDX_MCP_ACCESS_TOKEN` set in the environment. This checks external discovery and an actual read-only invocation; it does not test ChatGPT. ChatGPT account/workspace connector availability and UI may depend on the active ChatGPT plan and admin settings.

Do not paste access tokens or secret values into prompts. The download endpoint requires the authenticated owner context; it is not a public bearerless URL.
